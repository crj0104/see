## 1. 总体目标
本清单用于统一当前支付项目后端与即将新增的后台前端的代码细节标准，减少“能跑但不好维护”的问题。

## 2. Java 后端细节优化

### 2.1 DTO 与类型设计
- 跨层、跨服务、跨 MQ 的业务对象优先使用 DTO，避免使用裸 `Map`
- 枚举优先于魔法字符串，如通知状态、支付状态、渠道类型
- Controller 只接收 Request DTO，只返回 Response DTO
- 分页返回统一抽成分页 DTO，不要在不同接口里各自拼结构

### 2.2 Controller 层
- 所有管理后台接口统一挂在 `/api/v1/admin/**`
- 参数校验统一使用 `@Valid`
- Controller 不写业务逻辑，只做参数接收、权限校验、调用 service
- 文件上传、导出、重试、关单等危险操作明确审计日志

### 2.3 Service 层
- Service 方法命名体现动作语义，例如 `closeTransaction`、`retryNotification`
- 不在事务里发 HTTP、不做长耗时 IO、不直接调第三方
- 事务边界尽量收窄，先落库，再异步或事务外调用外部资源
- 重试逻辑写成明确状态机，不靠散落 if-else 叠加

### 2.4 持久层
- Mapper 只做数据读写，不掺杂业务判断
- 字段命名和 DDL 保持一致，避免代码列名、文档列名、SQL 列名三套说法
- 所有状态字段都建立索引策略，优先考虑查询路径
- 迁移脚本用 Flyway 或 Liquibase 版本化，不手改线上库

### 2.5 可观测性
- 接口日志、Service 耗时、MQ 消费日志都带 `traceId`
- 慢操作单独打 `warn`
- 第三方响应体、失败原因、HTTP 状态码保留到审计字段
- 后台所有危险操作必须记录操作人、时间、参数摘要

### 2.6 异常与幂等
- 统一全局异常处理
- 面向第三方协议的特殊接口允许局部 `try-catch`，但要在文档里写明原因
- 幂等逻辑放在切面或独立服务，不散落在各个业务方法里
- 重试次数、状态流转、终态定义必须代码和文档一致

## 3. Vue + TypeScript 前端细节优化

### 3.1 工程结构
- 前端单独项目 `payment-admin-web`
- 页面放在 `src/pages`
- 通用业务组件放在 `src/components`
- API 请求放在 `src/services`
- 类型声明放在 `src/types`
- 组合式登录态、筛选逻辑放在 `src/composables`
- 工具函数放在 `src/utils`

### 3.2 组件设计
- 一个组件一个职责，复杂页面拆为筛选区、表格区、详情区、操作区
- 单个组件尽量控制在 200 行左右
- 表格列定义、状态映射、标签色值抽离为常量
- JSON 展示、状态徽章、时间线、空态面板做成可复用组件
- Vue 组件统一使用 `script setup` + Composition API

### 3.3 请求层
- 统一封装 `request.ts`
- 统一处理 token 注入、错误弹窗、401 失效跳转、分页参数
- 不在页面里直接拼接 URL 和处理底层异常
- 所有接口类型声明与页面数据模型同步维护

### 3.4 状态管理
- 登录态、用户信息、菜单权限优先收敛到单一会话 composable
- 页面筛选条件按模块拆 composable 或页面内状态，不把所有状态堆在一个全局仓库
- 抽屉开关、弹窗开关这类纯本地 UI 状态优先放组件内部

### 3.5 交互细节
- 列表页优先支持回车搜索、重置筛选、状态高亮
- 危险操作需要二次确认
- 失败响应显示可读错误，不直接暴露后端堆栈
- 加载、空态、错误态、无权限态都必须单独设计

### 3.6 样式与视觉
- 统一使用设计令牌：颜色、圆角、阴影、间距、字号
- 避免内联样式横飞，优先沉淀为通用样式类或组件变体
- 后台设计以稳定、专业、可读为主，不追求花哨炫技
- 图表、表格、标签、抽屉、弹窗保持统一视觉语言

## 4. 推荐下一步优化项
- 为 `payment-admin-service` 补齐商户、通知、退款、对账聚合接口
- 为管理后台补齐 RBAC 与审计日志
- 为前端增加统一权限路由守卫
- 为关键页面增加单元测试与联调验证
- 为所有 SQL 变更全面接入 Flyway

## 5. Controller 组织细节
- 一个服务只有一个 Controller 不一定是问题，关键看这个服务是不是单一边界上下文
- 如果同一个 Controller 同时承担外部回调、后台管理、内部聚合、批处理命令，就应该拆分类
- 推荐拆分维度：按调用方拆 `External*Controller` / `Admin*Controller` / `Internal*Controller`
- 推荐拆分维度：按职责拆 `QueryController` / `CommandController` / `BatchController`
- Controller 变多不是目的，边界清晰、协议稳定、代码可维护才是目的
