## 1. Java 语言特性

### 1.1 虚拟线程 (Virtual Threads)

**为什么需要？**
传统上，Tomcat 用的是"一个请求一个线程"（Platform Thread）模型。但 OS 线程创建成本高（≈1MB 栈内存），而且线程在 IO 等待时（比如调 Redis、等数据库）会被白白阻塞着不能做别的事。一台机器几千个 OS 线程就到极限了，高并发下很容易 OOM。

**原理是什么？**
Java 21 虚拟线程是 JVM 管理的轻量级线程，不是 OS 线程。它们由 JVM 调度到少量的 Carrier Thread（载体线程，默认就是 Platform Thread 池）上运行。关键点是：**当虚拟线程执行 IO 阻塞操作（Socket 读写、数据库查询）时，会自动 yield 让出 Carrier Thread，让其他虚拟线程跑**，OS 层面没有线程被阻塞。

```
Platform Thread 模型：           Virtual Thread 模型：
                                 
[请求1→线程1→IO阻塞→空闲]       [请求1→VT1→IO阻塞→yield]
[请求2→线程2→运行中   ]       [请求2→VT2→运行中→占用Carrier]
[请求3→线程3→等待创建  ]       [请求3→VT3→等待轻量调度  ]
                              [请求1→VT1→IO完成→恢复运行]
```

**代码怎么用？**
```yaml
# application.yml — 一行配置开启
spring:
  threads:
    virtual:
      enabled: true    # Tomcat 自动换用虚拟线程执行器
```
开了之后，每个请求还是走 Tomcat，但处理请求的工作线程变成了虚拟线程，Tomcat 可以轻松处理数万个并发请求。

### 1.2 构造方法注入 (Constructor Injection)

**为什么需要？**
Spring 有三种依赖注入方式：字段注入、Setter 注入、构造方法注入。
- **字段注入**（`@Autowired private Xxx xxx`）最简单，但问题很多：无法用 `final` 关键字、单元测试必须靠 Spring 启动、编译时不检查依赖是否完整。
- **构造方法注入**按"不给就用不了"的原则，缺了哪个依赖编译就直接报错。

**原理是什么？**
Spring 在创建 Bean 时，如果只有一个构造方法（或者是 `@Autowired` 标注的构造方法），会自动从容器中查找匹配的参数传入。Lombok 的 `@RequiredArgsConstructor` 正是利用这个机制——它为所有 `final` 字段生成一个构造方法，Spring 自动调用注入。

```java
// 字段注入（不推荐）
@Autowired
private PaymentMapper paymentMapper;        // 编译不检查，运行时可能 null

// 构造方法注入（推荐）
@Service
public class PaymentServiceImpl implements PaymentService {
    private final PaymentMapper paymentMapper;     // final 保证不可变
    private final IdempotentService idempotentService;

    // 构造方法 — Spring 自动注入
    public PaymentServiceImpl(PaymentMapper paymentMapper,
                               IdempotentService idempotentService) {
        this.paymentMapper = paymentMapper;
        this.idempotentService = idempotentService;
    }
}

// 用 Lombok 简化
@RequiredArgsConstructor    // 为 final 字段自动生成构造方法
@Service
public class PaymentServiceImpl implements PaymentService {
    private final PaymentMapper paymentMapper;
    private final IdempotentService idempotentService;
    // 效果和上面完全一样
}
```

### 1.3 `@NonNull` / `@Nullable` 空安全注解

**为什么需要？**
Java 没有内置的 null-safety 机制。Spring 提供了 `@NonNull` 和 `@Nullable` 注解，配合 IDE 的静态分析，可以在编译期发现"可能为 null"的代码路径，避免 NullPointerException。

**原理是什么？**
这些注解本质是**契约标注**（Contract Annotation）——告诉调用方这个返回值和参数会不会是 null。IDE（IntelliJ / VS Code）会读取这些注解做静态分析，如果代码逻辑可能违反契约就给出警告。

```java
// @NonNull：承诺返回值不会为 null
public @NonNull Flux<DataBuffer> getBody() {
    return Flux.just(bufferFactory.wrap(bodyBytes));
    // IDE 知道这里不会返回 null，调用方不用判空
}

// @Nullable：参数可能为 null，调用方需要处理
public void sendNotification(@Nullable String notifyContent) {
    String content = notifyContent != null ? notifyContent : "";
}
```

### 1.4 UUID / SHA-256 / HMAC-SHA256

**为什么需要？**
支付系统中有三个高频需求：1) 生成全局唯一的 ID（交易号、Nonce、幂等键）——用 UUID；2) 对请求体做防篡改摘要——用 SHA-256；3) API 签名防伪造——用 HMAC-SHA256。

**原理是什么？**
- **UUID**：128 位随机数，碰撞概率极低（2^122 分之一）。`UUID.randomUUID()` 使用 SecureRandom 生成，比简单随机数更安全。
- **SHA-256**：不可逆的哈希函数。输入任何长度都输出 256 位（32 字节）固定长度摘要。无法从摘要反推原文，而且原文改一个 bit，摘要就完全不同（雪崩效应）。
- **HMAC-SHA256**：用密钥参与的哈希计算。**同样的载荷，不同的密钥产生不同的签名**。这是 API 鉴权的根基——攻击者不知道密钥就伪造不了签名。

```java
// UUID
String nonce = UUID.randomUUID().toString();  // → a1b2c3d4-e5f6-...

// SHA-256 — 对请求体做摘要
MessageDigest digest = MessageDigest.getInstance("SHA-256");
byte[] hash = digest.digest(bodyBytes);       // 32 字节二进制

// HMAC-SHA256 — 带密钥的签名
Mac mac = Mac.getInstance("HmacSHA256");
SecretKeySpec keySpec = new SecretKeySpec(secret.getBytes(UTF_8), "HmacSHA256");
mac.init(keySpec);
byte[] signature = mac.doFinal(payload.getBytes(UTF_8));
```

## 2. 基础通用技术

### 2.1 Maven 多模块 (Multi-Module)

**为什么需要？**
支付中台有 7 个微服务，它们共享一些公共代码：统一的响应格式 `ApiResponse`、异常体系 `PaymentException`、链路追踪工具类等。如果不做多模块，要么把公共代码在每个服务里复制一份（难维护），要么打包成独立的 jar 手工管理版本（繁琐）。Maven 多模块让这些服务在同一个项目中协同开发，公共代码放 `payment-common`，其他模块直接引用。

**原理是什么？**
Maven 多模块在父 POM 中声明 `<modules>`，子模块通过 `<parent>` 指向父 POM。关键机制是 `<dependencyManagement>`——在父 POM 里统一定义所有依赖的版本号，子模块引用时不用写版本，做到**"一个地方改版本，所有模块生效"**。构建时 Maven 按模块依赖顺序编译（先 common → 再其他服务）。

```xml
<!-- pom.xml（父 POM）-->
<groupId>com.payment.core</groupId>
<artifactId>distributed-payment-core-platform</artifactId>
<version>1.0.0</version>
<packaging>pom</packaging>                      <!-- 父模块必须是 pom 打包类型 -->

<modules>
    <module>payment-common</module>              <!-- 公共模块，排第一，先构建 -->
    <module>payment-api-gateway</module>
    <module>payment-transaction-service</module>
    <!-- ... 共 8 个模块 -->
</modules>

<properties>
    <java.version>21</java.version>
    <mybatis-plus.version>3.5.6</mybatis-plus.version>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
            <version>${mybatis-plus.version}</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

```xml
<!-- payment-transaction-service/pom.xml（子模块）-->
<parent>
    <groupId>com.payment.core</groupId>
    <artifactId>distributed-payment-core-platform</artifactId>
    <version>1.0.0</version>
</parent>

<dependencies>
    <dependency>
        <groupId>com.payment.core</groupId>
        <artifactId>payment-common</artifactId>   <!-- 引用兄弟模块 -->
    </dependency>
    <dependency>
        <groupId>com.baomidou</groupId>
        <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
        <!-- 不用写版本，从父 POM 继承 -->
    </dependency>
</dependencies>
```

**依赖排除技巧**：Gateway 引用了 `payment-common`，但 Gateway 是基于 WebFlux（Reactive）的，不需要 `spring-boot-starter-web` 和 MyBatis-Plus，需要用 `<exclusions>` 排除掉，否则启动冲突。

```xml
<dependency>
    <groupId>com.payment.core</groupId>
    <artifactId>payment-common</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>   <!-- MVC vs Reactive 冲突 -->
        </exclusion>
        <exclusion>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-spring-boot3-starter</artifactId>  <!-- DataSource 冲突 -->
        </exclusion>
    </exclusions>
</dependency>
```

### 2.2 Lombok

**为什么需要？**
Java Bean 需要大量样板代码：getter/setter、toString、equals/hashCode、构造器。如果手写，一个简单的 DTO 要上百行。Lombok 通过编译期注解处理（Annotation Processor），自动生成这些代码。

**原理是什么？**
Lombok 在 `javac` 编译阶段插入一个 **Annotation Processor**，扫描 `@Data`、`@Builder` 等注解，在生成 `.class` 文件之前修改 AST（抽象语法树）注入对应的方法。所以源码里看不到 getter/setter，但编译后的字节码里有。正因为它在编译期工作，IDE 需要装 Lombok 插件才能正确提示代码补全。

```java
// @Data = @Getter + @Setter + @ToString + @EqualsAndHashCode
// @Builder = 生成链式调用的构造器
// @NoArgsConstructor = 无参构造（MyBatis-Plus Entity 需要）
// @AllArgsConstructor = 全参构造（@Builder 需要）

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class PaymentTransaction {
    private String transactionId;
    private BigDecimal amount;
    private String status;
}

// @Builder 的使用效果：
PaymentTransaction tx = PaymentTransaction.builder()
        .transactionId(UUID.randomUUID().toString())
        .amount(new BigDecimal("99.00"))
        .status("INIT")
        .build();
// 不用写 new 然后 set 四个字段

// @RequiredArgsConstructor — 自动生成构造方法注入
@RequiredArgsConstructor
@Service
public class PaymentServiceImpl implements PaymentService {
    private final PaymentMapper paymentMapper;    // 自动成为构造参数
    private final IdempotentService idempotentService;
}
// 等价于手动写了下面这个构造器：
// public PaymentServiceImpl(PaymentMapper p, IdempotentService i) {
//     this.paymentMapper = p; this.idempotentService = i;
// }

// @Slf4j — 自动注入 log 对象，不用手动定义 Logger
@Slf4j
@Service
public class NotificationServiceImpl implements NotificationService {
    public void send() {
        log.info("Sending notification to {}", url);
        // 等价于：
        // private static final Logger log = LoggerFactory.getLogger(getClass());
    }
}
```

### 2.3 SLF4J + Logback + MDC

**为什么需要？**
分布式系统里一笔请求要经过 Gateway → Transaction → Channel 等多个服务。如果各服务各打各的日志，出了问题很难串起来排查。MDC（Mapped Diagnostic Context）解决了这个问题：在请求入口处生成一个全局唯一的 TraceId，放入日志上下文，后续所有日志都会自动带上这个 TraceId，按它一搜就能串起整条调用链。

**原理是什么？**
SLF4J 是日志的门面（Facade），不干活，只定义 API。Logback 是具体实现（类似 Log4j2）。MDC 是 SLF4J 提供的一个**线程绑定的 Map**，底层是 `ThreadLocal`。你在一个线程中 `MDC.put("traceId", value)`，该线程后续所有日志通过 `%X{traceId}` pattern 自动输出这个值。**关键问题是**：`ThreadLocal` 在请求结束时必须清理，否则线程池复用时下一个请求会读到上一个请求的 TraceId（称为"串号"）。

```java
// 1. Logger 获取（两种方式等价）
@Slf4j
public class XxxService {
    public void process() {
        log.info("这条日志会自动带 TraceId");  // 如果有 MDC
    }
}
// 等价于：
public class XxxService {
    private static final Logger log = LoggerFactory.getLogger(XxxService.class);
}

// 2. MDC 设置与清理（最重要的模式）
@Component
public class TraceIdFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        try {
            // 从请求头取上游传来的 TraceId
            String traceId = null;
            if (request instanceof HttpServletRequest httpRequest) {
                traceId = httpRequest.getHeader("X-Trace-Id");
            }
            if (!StringUtils.hasText(traceId)) {
                traceId = UUID.randomUUID().toString().replace("-", "");
            }

            MDC.put("traceId", traceId);   // ← 放入 MDC，日志自动输出

            chain.doFilter(request, response);
        } finally {
            MDC.clear();                   // ← 必须清理！否则线程池复用串号
        }
    }
}
```

```xml
<!-- logback-spring-base.xml — %X{traceId} 是关键 -->
<encoder>
    <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId}] - %msg%n</pattern>
</encoder>
```
> `%X{traceId}` 的含义是：输出 MDC 中 key 为 `traceId` 的值。如果 MDC 里没有，就输出空。

```yaml
# application.yml — 日志级别控制
logging:
  level:
    com.payment.core.transaction: INFO     # 业务日志 INFO 级别
    org.springframework.web: WARN           # Spring 框架日志只输出 WARN+
```

### 2.4 Jackson JSON

**为什么需要？**
微服务之间通过 JSON 通信。统一的序列化/反序列化机制是所有 RPC 的基础。Jackson 是 Spring Boot 默认的 JSON 处理库。

**原理是什么？**
`ObjectMapper` 是 Jackson 的核心类：`writeValue()` 把 Java 对象转成 JSON（序列化），`readValue()` 把 JSON 转成 Java 对象（反序列化）。Spring Boot 自动配置一个全局 `ObjectMapper` Bean，可以通过 `spring.jackson.*` 配置。`@JsonInclude(Include.NON_NULL)` 告诉 Jackson：序列化时**跳过 null 字段**，减少 JSON 体积。`Serializable` 接口标记类可以被 Java 原生序列化机制处理，是 RPC 框架的通用约定。

```java
// ApiResponse<T> — 统一响应基类
@Data
@Builder
@JsonInclude(Include.NON_NULL)    // null 字段不序列化，响应体更简洁
public class ApiResponse<T> implements Serializable {
    private int code;
    private String message;
    private T data;
    private long timestamp;

    public static <T> ApiResponse<T> success(T data) {
        return ApiResponse.<T>builder()
                .code(200).message("success").data(data)
                .timestamp(Instant.now().toEpochMilli())
                .build();
    }
}

// 返回效果：data=null 时 "data" 字段直接被省略
// ApiResponse.success(dashboardDTO)
// → {"code":200,"message":"success","data":{"merchantCount":100,...},"timestamp":...}
// ApiResponse.success(null)
// → {"code":200,"message":"success","timestamp":...}  ← data 字段不出现

// objectMapper.convertValue() — Map 转 DTO
// 场景：Feign 返回的数据类型擦除（?）了，拿到的是 Map，需要转回具体 DTO
@SuppressWarnings("unchecked")
private <T> Page<T> extractPage(ApiResponse<?> response, Class<T> itemType) {
    Map<String, Object> pageMap = objectMapper.convertValue(response.getData(), Map.class);
    long total = ((Number) pageMap.get("total")).longValue();
    List<Map<String, Object>> records = (List<Map<String, Object>>) pageMap.get("records");
    List<T> items = records.stream()
            .map(r -> objectMapper.convertValue(r, itemType))   // Map → DTO
            .toList();
    Page<T> result = new Page<>();
    result.setRecords(items);
    result.setTotal(total);
    return result;
}
```

### 2.5 java.time 时间 API (JSR-310)

**为什么需要？**
Java 8 之前的 `Date` 和 `Calendar` 设计糟糕：可变（线程不安全）、月份从 0 开始、命名混乱（`Date.getMonth()` 返回 0-11）。JSR-310 重新设计了时间 API，所有类都是**不可变的**（Immutabl），线程安全，方法命名清晰。

**原理是什么？**
- `LocalDateTime`：带日期和时间的对象（"2025-05-14T10:30:00"），不关联时区。适合大多数业务场景。
- `LocalDate`：只有日期，没有时间。适合对账日期这类只需要日期的场景。
- `Instant`：时间戳，自 1970-01-01T00:00:00Z 起的纳秒数。适合跨时区的时间表示。
- `DateTimeFormatter`：线程安全的日期格式化类（替代 `SimpleDateFormat`，后者线程不安全）。

```java
// 常用操作
LocalDateTime now = LocalDateTime.now();         // 2025-05-14T10:30:00
LocalDate today = LocalDate.now();               // 2025-05-14
Instant timestamp = Instant.now();               // 1735000000（毫秒时间戳，与时区无关）

// 格式化
DateTimeFormatter fmt = DateTimeFormatter.ofPattern("yyyy-MM-dd");
String dateStr = today.format(fmt);              // "2025-05-14"

// 解析
LocalDate parsed = LocalDate.parse("2025-05-14");
LocalDateTime dateTime = LocalDateTime.parse("2025-05-14T10:30:00");

// 日期计算（不可变，返回新对象）
LocalDate yesterday = today.minusDays(1);        // 前一天
LocalDateTime oneHourLater = now.plusHours(1);   // 后一小时
```

### 2.6 Stream API

**为什么需要？**
传统的 for 循环写集合操作又长又容易出错（特别是遍历时修改集合）。Stream API 让代码写"做什么"而不是"怎么做"——声明式编程，代码更短、更易读、更容易并行。

**原理是什么？**
Stream 是一个**数据管道**，分三步：1) **创建流**（`.stream()`）；2) **中间操作**（`.map()`、`.filter()`、`.sorted()`）——它们是懒惰的，不立即执行，只是记录操作；3) **终端操作**（`.toList()`、`.collect()`、`.forEach()`）——触发实际计算。这种机制叫"惰性求值"，好处是可以优化执行顺序（比如 `filter` + `limit` 可以提前终止）。

```java
// 场景1：Entity 列表转 DTO 列表（最常用）
List<NotificationRecord> records = mapper.selectList(wrapper);
List<NotificationDTO> dtoList = records.stream()       // 创建流
        .map(r -> NotificationDTO.builder()            // 中间：转换
                .id(r.getId())
                .transactionId(r.getTransactionId())
                .notificationStatus(r.getNotificationStatus())
                .build())
        .toList();                                     // 终端：收集

// 场景2：过滤
records.stream()
        .filter(r -> "PENDING".equals(r.getStatus()))  // 只保留 PENDING 状态
        .toList();

// 场景3：生成数据
IntStream.range(0, 7).forEach(i -> {
    trends.add(DashboardTrendDTO.builder()
            .date(today.minusDays(i).toString())
            .transactionCount(i * 100)
            .build());
});
```

### 2.7 Optional

**为什么需要？**
null 引用的发明者 Tony Hoare 称之为"十亿美元的错误"。Java 中最常见的 NPE 就是调用了 null 对象的方法。`Optional` 是一个**容器**，明确告诉开发者"这个值可能为空，你必须处理"。

**原理是什么？**
`Optional<T>` 要么包装一个值（`isPresent() == true`），要么是空的（`isEmpty() == true`）。关键不是怎么创建，而是**作为方法返回值类型**——看到方法返回 `Optional<String>`，就知道结果可能为空，强迫调用方用 `orElse()`、`ifPresent()` 等方法处理，不会不小心就 NPE。

```java
// 用法1：处理可能为 null 的值
String query = Optional.ofNullable(request.getURI().getRawQuery()).orElse("");
// 等价于：String query = request.getURI().getRawQuery() != null ? ... : "";

// 用法2：作为方法返回值，明确告知可能无结果
public Optional<String> getCachedResult(String key) {
    String result = redisTemplate.opsForValue().get(cacheKey(key));
    return Optional.ofNullable(result);  // null → Optional.empty()，有值 → Optional.of()
}

// 调用方必须处理空值
Optional<String> cached = idempotentService.getCachedResult(key);
if (cached.isPresent()) {
    return cached.get();        // 有缓存 → 直接返回
} else {
    return processPayment();    // 没有缓存 → 执行业务
}
```

### 2.8 Enum 枚举

**为什么需要？**
状态码如果用字符串常量（`"SUCCESS"`、`"FAILED"`），手写容易拼错，而且没有类型安全。Enum 把相关的常量组织在一起，编译器检查类型匹配，还能带属性和方法。

**原理是什么？**
Java 的 Enum 本质上是继承了 `java.lang.Enum` 的类。每个枚举常量是那个类的静态实例。可以像普通类一样定义字段、构造方法和实例方法。本项目中的枚举都带 `code` 和 `description` 字段，支持从编码反查枚举值的 `fromCode()` 静态方法——这个模式在支付系统中非常常见。

```java
public enum PaymentStatus {
    INIT("INIT", "初始创建"),
    PENDING("PENDING", "处理中"),
    SUCCESS("SUCCESS", "支付成功"),
    FAILED("FAILED", "支付失败"),
    CLOSED("CLOSED", "已关单");

    private final String code;
    private final String description;

    // 构造方法
    PaymentStatus(String code, String description) {
        this.code = code;
        this.description = description;
    }

    public String getCode() { return code; }
    public String getDescription() { return description; }

    // 从数据库状态码反查枚举值
    public static PaymentStatus fromCode(String code) {
        for (PaymentStatus s : values()) {
            if (s.code.equals(code)) return s;
        }
        throw new IllegalArgumentException("未知状态码: " + code);
    }
}

// 使用
PaymentStatus status = PaymentStatus.fromCode("SUCCESS");
System.out.println(status.getDescription());  // "支付成功"

// switch 表达式匹配（Java 14+）
String desc = switch (status) {
    case INIT -> "初始创建";
    case SUCCESS -> "支付成功";
    case FAILED -> "支付失败";
    default -> "未知";
};
```

### 2.9 泛型 (Generics)

**为什么需要？**
没有泛型之前，集合存什么类型都行（`List` 存 Object），取出要强制类型转换，运行时可能 `ClassCastException`。泛型让类型检查从运行时提前到编译期。

**原理是什么？**
泛型是编译期的类型检查机制。`ApiResponse<T>` 中的 `T` 是类型参数，编译器在编译时用具体类型替换它。**但 Java 的泛型是"擦除式"实现**——编译后的字节码中泛型信息被擦除了（变成 `Object`），只有元数据区保留签名供反射读取。这就是为什么运行时 `new T()` 不行，以及为什么 `objectMapper.convertValue()` 等框架级操作需要用 `Class<T>` 参数来绕过擦除。

```java
// ApiResponse<T> — T 可以是任意业务类型
ApiResponse<DashboardOverviewDTO> response1 = ApiResponse.success(overviewDTO);
// 编译时：T = DashboardOverviewDTO，data 字段类型被固定

ApiResponse<Page<MerchantSummaryDTO>> response2 = ApiResponse.success(page);
// 编译时：T = Page<MerchantSummaryDTO>，嵌套泛型也没问题

// 方法级泛型
private <T> T extractData(ApiResponse<?> response, Class<T> type) {
    // Class<T> 参数解决泛型擦除问题，运行时可以知道 T 的具体类型
    return objectMapper.convertValue(response.getData(), type);
}
```

### 2.11 并发工具 (java.util.concurrent)

**为什么需要？**
Gateway 的 Nonce 防重放原来用 Redis 实现，但后来排除了 Redis 依赖。需要换一种本地方案：既要线程安全（高并发防重），又要自动清理过期条目（不能内存泄漏）。`ConcurrentHashMap` + `ScheduledExecutorService` 正好解决。

**原理是什么？**
- **`ConcurrentHashMap`**：比 `synchronized` 的 `Hashtable` 效率高得多。它把内部数组分成多个 Segment（Java 8+ 使用 CAS + `synchronized` 只锁链表头节点），读操作基本无锁，写操作只锁影响的那一小段。
- **`ScheduledExecutorService`**：比 `Timer` 好，因为 Timer 一个线程挂了整个任务就停了，而 ScheduledExecutorService 有线程池兜底。
- **Daemon 线程**：把清理线程设为 `daemon=true`，表示它不阻止 JVM 关闭。所有业务线程跑完后，daemon 线程自动结束。

```java
public class InMemoryNonceStore {
    // ConcurrentHashMap — 高并发安全的 KV 存储
    private final ConcurrentHashMap<String, Long> store = new ConcurrentHashMap<>();

    // ScheduledExecutorService — 定时清理过期 nonce
    private final ScheduledExecutorService cleaner =
            Executors.newSingleThreadScheduledExecutor(r -> {
                Thread t = new Thread(r, "nonce-cleaner");
                t.setDaemon(true);   // 不阻止 JVM 退出
                return t;
            });

    public InMemoryNonceStore() {
        // 启动后每 60 秒执行一次清理
        cleaner.scheduleWithFixedDelay(this::evictExpired, 60, 60, TimeUnit.SECONDS);
    }

    // putIfAbsent — 原子操作："不存在才放进去"
    public boolean putIfAbsent(String key, long ttlSeconds) {
        long expiresAt = Instant.now().toEpochMilli() + ttlSeconds * 1000;
        Long previous = store.putIfAbsent(key, expiresAt);
        return previous == null;  // null = 首次写入，非 null = 已存在（重复请求）
    }

    // 清理过期条目
    private void evictExpired() {
        long now = Instant.now().toEpochMilli();
        store.values().removeIf(expiresAt -> expiresAt < now);
    }
}
```

### 2.12 Lambda + 函数式接口

**为什么需要？**
传统匿名内部类很啰嗦（`new Runnable() { @Override public void run() { ... } }`）。Lambda 表达式让代码更简洁——"只关心参数和逻辑，不关心实现类叫什么"。

**原理是什么？**
Lambda 表达式本质上是**函数式接口**（只有一个抽象方法的接口，如 `Runnable`、`Supplier<T>`）的匿名实现。编译时 `() -> {}` 会被编译成 `invokedynamic` 指令，JVM 在运行时才决定如何创建这个函数对象。比匿名内部类高效（不需要生成额外的 `.class` 文件）。

```java
// 项目中的典型用法：Supplier<T> 包装可能抛异常的操作
//
// 问题：多次调用 countXxx()，每个都要 try/catch，代码重复
// 解决：用 Supplier<Long> 把计数操作包装成一个参数，统一 try/catch

private long safeCount(Supplier<Long> counter) {
    try {
        return counter.get();      // 执行传入的计数逻辑
    } catch (Exception e) {
        log.warn("Count failed", e);
        return 0;                  // 失败时返回 0，不影响 Dashboard 展示
    }
}

// 调用方 — 传入方法引用或 Lambda
long txCount = safeCount(transactionAdminService::countTransactions);
// 等价于：safeCount(() -> transactionAdminService.countTransactions())
long pendingCount = safeCount(() -> notificationAdminService.countPending());
long merchantsCount = safeCount(merchantAdminService::countMerchants);
```

### 2.13 Jakarta Bean Validation

**为什么需要？**
用户在 Controller 里手写 if/else 校验参数又长又容易遗漏。声明式校验（注解）把校验规则写在 DTO 字段上，框架自动执行，结果也自动返回。

**原理是什么？**
Spring Boot 集成了 Hibernate Validator（JSR-380 的实现）。在 Controller 方法参数上标注 `@Valid`，Spring 在进入方法前反射读取参数对象的校验注解，逐个验证。如果失败，抛出 `MethodArgumentNotValidException`，被 `GlobalExceptionHandler` 捕获处理。

```java
// DTO 上声明校验规则
public class CreatePaymentRequest {
    @NotBlank(message = "商户号不能为空")
    private String merchantId;

    @NotNull(message = "金额不能为空")
    private BigDecimal amount;

    @NotBlank(message = "幂等键不能为空")
    private String idempotentKey;
}

// Controller 上启用校验
@PostMapping("/payments")
public ApiResponse<PaymentResponse> createPayment(
        @Valid @RequestBody CreatePaymentRequest request) {  // ← @Valid 触发校验
    return ApiResponse.success(paymentService.createPayment(request));
}

// 校验失败时 GlobalExceptionHandler 拦截
@ExceptionHandler(MethodArgumentNotValidException.class)
public ApiResponse<Void> handleValidation(MethodArgumentNotValidException ex) {
    String msg = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> e.getField() + ":" + e.getDefaultMessage())
            .collect(Collectors.joining("；"));
    return ApiResponse.error(400, msg);
    // 返回 → {"code":400,"message":"商户号不能为空；金额不能为空"}
}
```

### 3.1 `@SpringBootApplication`

**为什么需要？**
一个 Spring Boot 应用需要三个基础注解才能工作：`@Configuration`（配置类）、`@EnableAutoConfiguration`（自动配置）、`@ComponentScan`（组件扫描）。每次写三个很麻烦，`@SpringBootApplication` 把它们打包成一个。

**原理是什么？**
`@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan`。`@EnableAutoConfiguration` 是核心——它读取所有 jar 中 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件，按条件（`@ConditionalOnClass`、`@ConditionalOnMissingBean` 等）加载自动配置类。

**为什么 Gateway 需要 `exclude`？**
Gateway 基于 WebFlux（Reactive），不连数据库。但自动配置扫描到 classpath 上有 `DataSource` 相关的类（来自 MyBatis-Plus starter）就会尝试配置数据源，发现没有 `spring.datasource.url` 就报错。用 `exclude = DataSourceAutoConfiguration.class` 告诉 Spring "这个自动配置类不要加载"。

```java
// 标准 Spring Boot 应用
@SpringBootApplication
@EnableDiscoveryClient
public class PaymentTransactionApplication {
    public static void main(String[] args) {
        SpringApplication.run(PaymentTransactionApplication.class, args);
    }
}

// Gateway 特殊处理：排除数据源自动配置
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
@EnableDiscoveryClient
public class PaymentGatewayApplication {
    public static void main(String[] args) {
        SpringApplication.run(PaymentGatewayApplication.class, args);
    }
}
```

### 3.2 `@Configuration` + `@Bean`

**为什么需要？**
Spring 管理 Bean 有两种方式：1) `@Component` + `@ComponentScan`（自动扫描）；2) `@Bean` 在 `@Configuration` 类中手动声明。第三种库的类（如 `RabbitTemplate`、`RestTemplate`）上没有 `@Component`，所以需要第二种方式手动注册。

**原理是什么？**
`@Configuration` 类会被 Spring CGLIB 代理，所有 `@Bean` 方法被拦截：同一个方法二次调用时，不从方法体新创建一个对象，而是直接从 Spring 容器返回已有的单例 Bean。这保证了 Bean 的单例特性。

```java
@Configuration
public class RabbitMQConfig {
    // @Bean 告诉 Spring：这个方法的返回值（TopicExchange）需要注册为一个 Bean
    @Bean
    public TopicExchange paymentExchange() {
        // 创建 TopicExchange 实例，放入 Spring 容器
        return new TopicExchange("payment.exchange");
    }

    @Bean
    public Queue paymentResultQueue() {
        return QueueBuilder.durable("payment.result.queue")
                .deadLetterExchange("payment.dlx")       // 绑定死信交换机
                .deadLetterRoutingKey("payment.dead")
                .build();
    }

    @Bean
    public Jackson2JsonMessageConverter jsonMessageConverter() {
        // 把 JSON 转换器注册为 Bean，RabbitTemplate 自动使用它
        return new Jackson2JsonMessageConverter();
    }
}
```

### 3.5 Spring AOP

**为什么需要？**
支付系统有大量"横切关注点"（Cross-Cutting Concerns）：日志记录、幂等检查、权限校验。如果在每个业务方法里都写一遍，不仅代码大量重复，还容易遗漏。AOP 把这些关注点从业务代码中抽离出来，织入到目标方法的前后。

**原理是什么？**
Spring AOP 基于**动态代理**（默认 JDK 动态代理，类无接口时用 CGLIB）。`@Around` 通知在目标方法调用前后插入自定义逻辑：
1. 方法调用前：提取幂等键 → 尝试获取分布式锁
2. 调用目标方法：`joinPoint.proceed()`
3. 调用后：缓存成功结果或释放锁

**最核心的实例：幂等注解 AOP**

```java
// 1. 先定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    long ttl() default 86400;            // 默认 24 小时内相同 key 的请求只处理一次
    boolean fetchResult() default true;   // 重复请求是否返回上一次的结果
}

// 2. 在需要幂等的方法上加注解
@Idempotent(ttl = 86400)
@PostMapping("/payments")
public ApiResponse<PaymentResponse> createPayment(@RequestBody CreatePaymentRequest request) {
    return ApiResponse.success(paymentService.createPayment(request));
}

// 3. AOP 切面实现幂等逻辑
@Aspect
@Component
public class IdempotentAspect {
    private final IdempotentService idempotentService;

    // @Around 注解绑定：当调用带 @Idempotent 的方法时，先执行这里
    @Around("@annotation(idempotent)")
    public Object handleIdempotent(ProceedingJoinPoint joinPoint, Idempotent idempotent)
            throws Throwable {

        String key = extractIdempotentKey(joinPoint);     // 从参数中提取幂等键

        // 步骤1：尝试获取分布式锁（SETNX）
        boolean acquired = idempotentService.tryAcquire(key, idempotent.ttl());

        if (!acquired) {
            // 步骤2：没拿到锁 → 可能是重复请求
            if (idempotent.fetchResult()) {
                // 尝试取上一次的缓存结果
                Optional<String> cached = idempotentService.getCachedResult(key);
                if (cached.isPresent()) {
                    return cached.get();    // 返回上次的处理结果
                }
            }
            throw new BizException(ErrorCode.IDEMPOTENT_CONFLICT, "重复请求");
        }

        try {
            // 步骤3：拿到锁 → 执行业务方法
            Object result = joinPoint.proceed();
            // 步骤4：缓存成功结果
            idempotentService.markProcessed(key, result);
            return result;
        } catch (Exception e) {
            // 步骤5：业务失败 → 释放锁，让用户可以重试
            idempotentService.remove(key);
            throw e;
        }
    }
}
```

**第二个实例：AOP 日志切面**

```java
@Aspect
@Component
@ConditionalOnWebApplication(type = SERVLET)   // 只在 MVC 服务中生效
public class WebLogAspect {

        } catch (Throwable e) {
            log.error("{} 失败, 耗时={}ms, 原因={}",
                    joinPoint.getSignature().getName(),
                    System.currentTimeMillis() - start, e.getMessage());

        }
    }
}
```

### 3.6 `@Transactional`

**为什么需要？**
Outbox 模式要求"写业务表"和"写 outbox 表"在同一个事务中——要么都成功，要么都失败。如果没有事务，业务表写成功了但 outbox 表写入前进程崩溃了，消息就永远发不出去了。

**原理是什么？**
Spring 的声明式事务使用 AOP 代理：在方法开始时开启数据库连接的事务（`connection.setAutoCommit(false)`），方法正常结束时提交（`connection.commit()`），抛出异常时回滚（`connection.rollback()`）。默认只回滚 `RuntimeException`，`rollbackFor = Exception.class` 让所有异常都回滚。

```java
@Service
public class PaymentServiceImpl implements PaymentService {

    @Transactional(rollbackFor = Exception.class)   // 任何异常都回滚
    public PaymentTransaction createPayment(CreatePaymentRequest request) {
        // 1. 写业务表
        PaymentTransaction tx = PaymentTransaction.builder()
                .transactionId(generateId())
                .amount(request.getAmount())
                .status("INIT")
                .build();
        paymentMapper.insert(tx);    // SQL: INSERT INTO payment_transaction ...

        // 2. 写 Outbox 表（同一事务）
        OutboxEntity outbox = OutboxEntity.builder()
                .aggregateId(tx.getTransactionId())
                .eventType("PAYMENT_CREATED")
                .status("PENDING")              // 待投递
                .build();
        outboxMapper.insert(outbox); // SQL: INSERT INTO outbox_entity ...
        // 两个 insert 要么都提交，要么都回滚
        return tx;
    }
}
```

### 3.7 `@Scheduled` 定时任务

**为什么需要？**
支付系统有很多不依赖用户请求的后台任务：Outbox 消息轮询、超时关单、自动对账。它们需要定时自动执行。

**原理是什么？**
`@EnableScheduling` 让 Spring 注册一个 `ScheduledAnnotationBeanPostProcessor`，扫描所有 `@Scheduled` 方法，用 `ScheduledExecutorService` 按配置的频率调度执行。`fixedDelay` 是"上次执行结束后隔多久执行下一次"（适合轮询），`cron` 是"指定时间点执行"（适合对账等固定时间任务）。

```java
// fixedDelay：上次执行完等 2 秒后再执行下一次（适合轮询任务）
@Scheduled(fixedDelay = 2000)
public void processOutbox() {
    // 每 2 秒扫描待发送的 outbox 消息
    List<OutboxEntity> pending = outboxMapper.selectPendingList();
    for (OutboxEntity outbox : pending) {
        rabbitTemplate.convertAndSend(exchange, routingKey, outbox.getPayload());
        outboxMapper.markProcessed(outbox.getId());
    }
}

// cron 表达式：每天凌晨 2 点执行
@Scheduled(cron = "0 0 2 * * ?")
public void autoReconcile() {
    // T+1 自动对账
    reconciliationService.runReconciliation("MOCK", LocalDate.now().minusDays(1));
}
```

### 3.8 `@EnableAsync` + 线程池

**为什么需要？**
有些操作不需要同步等待结果（如发通知、写审计日志），可以异步执行。`@Async` 让方法在独立的线程池中执行，调用方不会阻塞。

**原理是什么？**
`@EnableAsync` 让 Spring 创建一个 AOP 切面，拦截 `@Async` 标注的方法，把方法提交到配置的 `Executor`（线程池）中执行，而不是在当前线程同步执行。

```java
@Configuration

@EnableScheduling
public class ThreadPoolConfig {
    @Bean("paymentExecutor")
    public Executor paymentExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(8);          // 核心线程数
        executor.setMaxPoolSize(16);          // 最大线程数
        executor.setQueueCapacity(200);       // 队列容量
        executor.setThreadNamePrefix("payment-exec-");
        executor.setRejectedExecutionHandler(new CallerRunsPolicy());  // 满队列时由调用方线程执行
        executor.initialize();
        return executor;
    }
}

// 使用
@Async("paymentExecutor")
public void sendNotificationAsync(String notifyUrl, String message) {
    restTemplate.postForEntity(notifyUrl, message, String.class);
    // 调用方立即返回，不等待 HTTP 响应
}
```

## 4. Spring Cloud 微服务体系

### 4.1 Spring Cloud Gateway

**为什么需要？**
微服务架构中，每个服务有不同的地址（`localhost:8081`、`localhost:8082`...），客户端不可能知道所有地址。Gateway 作为统一的入口层，负责：1) **路由**——按路径转发到不同的后端服务；2) **认证**——统一做签名验签，后端服务不用重复写；3) **限流**——统一流量治理。

**原理是什么？**
Spring Cloud Gateway 基于 WebFlux（Reactive），使用 Netty 作为底层服务器。核心是** Filter 链**：请求进入后，依次经过一系列 `GatewayFilter` 和 `GlobalFilter`（如鉴权 Filter、日志 Filter），最后到达路由目标。

```yaml
# 路由配置
spring:
  cloud:
    gateway:
      routes:
        - id: transaction-service
          uri: lb://payment-transaction-service   # lb:// = 通过 Nacos 负载均衡
          predicates:
            - Path=/api/v1/payments/**,/api/v1/refunds/**
```

**Filter 工作原理**：`GlobalFilter.filter(exchange, chain)` 中调 `chain.filter(exchange)` 交给下一个 Filter。Filter 可以在放行前和放行后插入逻辑，类似 Servlet Filter。

```java
// 全局 Filter 实现签名验签
@Component
public class ApiSignatureAuthFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        String path = request.getURI().getPath();

        if (isWhitelisted(path)) {                // 白名单跳过
            return chain.filter(exchange);
        }

        // 提取签名头
        String apiKey = trimHeader(request, "X-Api-Key");
        String signature = trimHeader(request, "X-Signature");
        String missing = findMissingHeader(apiKey, signature ...);
        if (missing != null) {
            return unauthorized(exchange, "Missing: " + missing);
        }

        // 验证签名（异步读取 body）
        return readBody(exchange).flatMap(bodyBytes ->
                Mono.fromCallable(() -> validateSignature(bodyBytes, apiKey, ...))
                        .subscribeOn(Schedulers.boundedElastic())
                        .flatMap(error -> {
                            if (error != null) return unauthorized(exchange, error);
                            return chain.filter(exchange.mutate()     // 放行
                                    .request(decorateRequest(request, bodyBytes, apiKey))
                                    .build());
                        }));
    }

    @Override
    public int getOrder() { return -60; }    // 高优先级，越早执行越好
}
```

**装饰器模式修改请求头**：Filter 验证通过后，需要告诉后端"这个请求已经认证过了"。`ServerHttpRequestDecorator` 是一个装饰器——它包装原始请求，重写部分方法（如 `getHeaders()` 注入 `X-Auth-Verified`）。

```java
private ServerHttpRequest decorateRequest(ServerHttpRequest request, byte[] bodyBytes, String apiKey) {
    return new ServerHttpRequestDecorator(request) {
        @Override
        public @NonNull HttpHeaders getHeaders() {
            HttpHeaders headers = new HttpHeaders();
            headers.putAll(super.getHeaders());
            headers.set("X-Auth-Verified", "true");    // 注入认证标记
            headers.setContentLength(bodyBytes.length);
            return headers;
        }
    };
}
```

### 4.2 OpenFeign

**为什么需要？**
微服务间需要相互调用（比如 Transaction Service 调用 Channel Service 发起支付）。如果每个服务都手写 HTTP 客户端，会有大量重复代码。Feign 把 HTTP 调用变成声明式的接口——你只定义接口和方法，Feign 自动实现序列化/反序列化和网络请求。

**原理是什么？**
Feign 使用 JDK 动态代理：在启动时扫描 `@FeignClient` 接口，为每个接口创建代理对象。调用接口方法时，代理对象根据 `@PostMapping`、`@GetMapping` 等注解构造 HTTP 请求、发送、解析响应。集成了 Sentinel 后，当 `fallback` 类被触发（服务不可用或超时），Feign 自动返回降级响应，不上抛异常。

```java
// 1. 定义 Feign 接口
@FeignClient(name = "payment-channel-service",
             path = "/api/v1/channels",
             fallback = ChannelServiceClientFallback.class)
public interface ChannelServiceClient {
    @PostMapping("/pay")
    ApiResponse<ChannelPayResponse> pay(@RequestBody ChannelPayRequest request);
}

// 2. 熔断降级实现
@Component
public class ChannelServiceClientFallback implements ChannelServiceClient {
    @Override
    public ApiResponse<ChannelPayResponse> pay(ChannelPayRequest request) {
        // 渠道服务不可用时，返回友好的降级响应
        return ApiResponse.error(503, "渠道服务暂时不可用");
    }
}

// 3. Feign 拦截器：自动注入签名（不需要每个调用处手动添加）
@Component
public class FeignAuthInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        template.header("X-Api-Key", apiKey);
        template.header("X-Timestamp", String.valueOf(Instant.now().toEpochMilli()));
        template.header("X-Nonce", UUID.randomUUID().toString());
        template.header("X-Signature", sign(template));
    }
}
```

### 4.3 Nacos 服务注册与发现

**为什么需要？**
微服务数量一多，各服务的地址就变成了动态变化的（扩缩容、宕机重启）。不能把地址硬编码在配置里。注册中心让服务启动时上报自己的地址，消费者通过服务名获取地址列表。

**原理是什么？**
Nacos 是一个注册中心 + 配置中心。服务注册的流程：
1. 服务启动时向 Nacos 注册自身（IP:Port + 服务名 + 心跳间隔）
2. Nacos 健康检查——定期向服务发心跳，如果收不到就标记为不健康
3. 消费者（Gateway）通过服务名 `lb://payment-transaction-service` 从 Nacos 获取服务地址列表
4. Nacos 返回健康节点，Gateway 做负载均衡（默认轮询）

```yaml

spring:

      discovery:
        server-addr: localhost:8848      # Nacos 地址
```

### 4.4 Sentinel 流量治理

**为什么需要？**
高并发下，突发流量可能打垮整个系统。需要三件事：1) **限流**——超过设定 QPS 的请求直接拒绝（保护后端）；2) **熔断**——下游服务不可用时快速失败，不等待超时（防止线程被拖死）；3) **降级**——返回降级响应而不是抛 500。

**原理是什么？**
Sentinel 使用"滑动窗口"做限流统计：把 1 秒分成多个小的统计窗口（如 500ms 一个），持续计算过去 1 秒的 QPS。超过阈值时触发 Block。网关层的限流先于业务处理，无效请求不会到达后端。

```java
// Gateway 层统一限流响应
@PostConstruct
public void initBlockHandler() {
    GatewayCallbackManager.setBlockHandler((ServerWebExchange exchange, Throwable t) -> {
        // 超过 QPS 阈值时，直接返回 429
        ServerResponse.status(HttpStatus.TOO_MANY_REQUESTS)
                .contentType(MediaType.APPLICATION_JSON)
                .body(BodyInserters.fromValue(Map.of(
                        "code", 429,
                        "message", "触发网关限流"
                )));
    });
}
```

```yaml
# Feign 熔断配置
feign:
  sentinel:
    enabled: true    # Feign 调用失败时触发 Sentinel 熔断
```

### 5.4 乐观锁（防并发覆盖）

**为什么需要？**
高并发下，两个请求同时更新同一条支付记录：请求 A 把它改成 SUCCESS，请求 B 把它改成 FAILED。如果没有锁，最终结果就是最后一个写入的覆盖前面的，但 A 和 B 都以为自己的操作成功了。

**原理是什么？**
乐观锁不是用数据库的锁，而是在 `UPDATE` 语句的 `WHERE` 条件中检查当前状态是否还是预期状态。如果状态已被其他请求修改，`UPDATE` 影响行数为 0，业务层据此判断"状态冲突"。

```java
// updateStatusAtomic 的 SQL：
// UPDATE payment_transaction SET status = 'CLOSED'
// WHERE transaction_id = 'TX001' AND status = 'SUCCESS'
//                                   ↑ 预期状态 → 如果已被别人改了就不更新

public void closeTransaction(String transactionId) {
    int rows = paymentTransactionMapper.updateStatusAtomic(
            transactionId,          // 要更新的记录
            "CLOSED",               // 目标状态
            "SUCCESS");             // 预期当前状态

    if (rows == 0) {
        // status != 'SUCCESS'，说明状态已被其他请求改变
        throw new BizException("交易状态已变更，不能关单");
    }
    // rows == 1 更新成功
}
```

## 6. 中间件 — Redis

### 6.1 Redis 幂等锁 (SETNX)

**为什么需要？**
幂等性的核心是一个分布式互斥锁：同一笔订单的第一次请求能处理，第二次重复请求时发现"锁已被占"就拒绝。Redis 的 SETNX 可以跨多个进程（跨服务实例）工作，比 Java 的 `synchronized` 更强。

**原理是什么？**
`SET key value NX EX ttl` 是一条原子指令：
- **NX** = Not Exist，key 不存在才设置（这就是互斥锁机制）
- **EX** = 过期时间，防止锁永远不释放（服务异常崩溃等）
- **原子性**：整个命令一起执行，没有竞态条件

```java
// Lua 脚本保证原子性
private static final String ACQUIRE_AND_CACHE_LUA = """
        local key = KEYS[1]
        local result = redis.call('SET', key, ARGV[1], 'NX', 'EX', ARGV[2])
        if result then
            return 1                -- 拿到锁，返回 1
        else
            return redis.call('GET', key)  -- 已存在，返回当前值（可能是 IN_PROGRESS 或 RESULT:xxx）
        end
        """;
```

**为什么用 Lua 脚本？** 因为有三个操作（SETNX、检查缓存、返回结果）需要一起执行，中间不能有其他 Redis 命令插进来。Lua 在 Redis 中原子执行整个脚本，不用事务。

```java
// IdempotentServiceImpl — 完整实现
@Service
public class IdempotentServiceImpl implements IdempotentService {

    private static final String KEY_PREFIX = "payment:idempotent:";
    private static final long DEFAULT_TTL_SECONDS = 86400;

    private final StringRedisTemplate redisTemplate;

    // tryAcquire — 先用 SETNX 尝试获取锁
    @Override
    public boolean tryAcquire(String idempotentKey, long ttlSeconds) {
        String key = KEY_PREFIX + idempotentKey;
        Boolean success = redisTemplate.opsForValue()
                .setIfAbsent(key, "IN_PROGRESS", ttlSeconds, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(success);
        // true = 首次请求，拿到锁；false = 重复请求，锁已被占
    }

    // tryAcquireAndCache — 一次性完成：尝试获取锁 或 返回已有缓存结果
    @Override
    public boolean tryAcquireAndCache(String idempotentKey, String resultJson, long ttlSeconds) {
        String key = KEY_PREFIX + idempotentKey;
        DefaultRedisScript<String> script = new DefaultRedisScript<>(ACQUIRE_AND_CACHE_LUA, String.class);
        String scriptResult = redisTemplate.execute(script,
                Collections.singletonList(key),
                "RESULT:" + resultJson, String.valueOf(ttlSeconds));

        if ("1".equals(scriptResult)) {
            return true;              // 拿到锁，执行业务
        }
        log.info("Idempotent hit: idempotentKey={}", idempotentKey);
        return false;                 // 重复请求，有缓存结果
    }

    // markProcessed — 业务执行成功后，缓存结果
    @Override
    public void markProcessed(String idempotentKey, String resultJson, long ttlSeconds) {
        String key = KEY_PREFIX + idempotentKey;
        redisTemplate.opsForValue().set(key, "RESULT:" + resultJson, ttlSeconds, TimeUnit.SECONDS);
    }

    // release — 业务失败，释放锁
    @Override
    public void release(String idempotentKey) {
        redisTemplate.delete(KEY_PREFIX + idempotentKey);
    }
}
```

**执行流程总结**：
```
请求 A（首次）          请求 B（重复）
    │                       │
    │  SETNX key            │  SETNX key
    │  → OK (拿到锁)         │  → 失败（锁已被 A 占）
    │                       │
    │  执行业务               │  GET key
    │  写数据库               │  → "RESULT:{json}"（已有缓存）
    │                       │
    │  SET key "RESULT:..." │  直接返回缓存结果
    │  释放                  │  （不执行业务）
    ▼                       ▼
```

### 6.2 INCR + EXPIRE 滑动窗口限流

**为什么需要？**
风控需要限制某个 IP 在单位时间内的请求次数（比如 1 分钟 10 次）。如果用固定时间窗口（比如每分钟重置一次），会出现"在 00:59 和 01:01 各请求 10 次"的临界问题。滑动窗口让限流更平滑。

**原理是什么？**
每次请求执行 `INCR key`，**当且仅当第一次返回 1 时**设置 `EXPIRE 60`。这样 key 存活 60 秒，这 60 秒内的请求次数就是计数器的值。60 秒后 key 自动过期，下一次请求又从 1 开始。虽然叫"滑动窗口"，实际上是通过过期时间模拟的近似滑动效果——每个 IP 的时间窗口从它第一次请求开始计算。

```java
@Component
@Order(20)
public class HighFrequencyRiskRule implements RiskRule {

    private static final String RISK_FREQ_PREFIX = "risk:freq:ip:";
    private static final int MAX_REQUESTS_PER_MINUTE = 10;   // 1 分钟最多 10 次

    private final StringRedisTemplate redisTemplate;

    public HighFrequencyRiskRule(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    @Override
    public void evaluate(RiskContext context) throws RiskException {
        if (context.getClientIp() == null) return;

        String key = RISK_FREQ_PREFIX + context.getClientIp();
        Long count = redisTemplate.opsForValue().increment(key);  // 原子自增，返回当前值

        if (count != null && count == 1) {
            // 第一次请求 → 设置过期时间（窗口起点）
            redisTemplate.expire(key, 1, TimeUnit.MINUTES);
        }

        if (count != null && count > MAX_REQUESTS_PER_MINUTE) {
            // 超过阈值 → 记录日志，抛出风控异常阻断交易
            log.warn("Risk Blocked: IP {} high frequency ({} requests)", context.getClientIp(), count);
            throw new RiskException(ErrorCode.RSK_HIGH_FREQUENCY, "请求频率过高");
        }
    }
}
```

**执行流程**：
```
时间轴                       计数器值    是否放行
10:30:00  请求1  INCR key →  1          放行
10:30:00  请求1  EXPIRE key 60 秒
10:30:05  请求2  INCR key →  2          放行
10:30:15  请求3  INCR key →  3          放行
...
10:30:55  请求11 INCR key →  11         阻断！抛出异常
10:31:00  key 过期，计数器重置
10:31:01  请求12 INCR key →  1          放行（新窗口开始）
```

**为什么不直接用 Redis 的 TTL 命令？**
因为 `INCR` 和 `EXPIRE` 是两个独立的命令，不是原子的。如果在 `INCR` 之后、`EXPIRE` 之前进程崩溃了，key 就没有过期时间，计数器永远不会重置，变成永久计数器导致内存泄漏。
解法是 `if (count == 1)` 才设 EXPIRE——**只有第一次请求设置过期时间**，后面的请求共享同一个过期时间。这样即使第一次之后崩溃，key 最多存 1 分钟。

### 6.3 Redis 配置与连接池 (Lettuce)

**为什么需要？**
高并发下 Redis 连接不能每次请求都新建（性能极差）。连接池（Connection Pool）维护一组长连接，请求时借用、用完归还。

**原理是什么？**
Spring Boot 2.x 后默认使用 Lettuce 作为 Redis 客户端。Lettuce 基于 Netty，是异步非阻塞的。连接池的 `max-active` 控制最大连接数，`min-idle` 控制最小空闲数。达到 `max-active` 后新请求阻塞等待。

```yaml
spring:

      host: localhost
      port: 6379
      database: 0
      timeout: 3000ms
      lettuce:
        pool:
          max-active: 32         # 最大连接数（高并发时调大）
          max-idle: 16           # 最大空闲连接
          min-idle: 4            # 最小空闲连接（预热时保留）
```

## 7. 中间件 — RabbitMQ

### 7.1 架构设计：为什么用 Topic 交换机？

**为什么需要？**
支付系统中有三类异步消息：1) 支付结果通知（Transaction → Notification）；2) 渠道回调结果（Channel → Transaction）；3) 对账触发。如果用直连队列（Direct Exchange），每个消息类型要写不同的配置，扩展性差。Topic Exchange 可以用通配符路由规则，一个交换机支持多种消息。

**原理是什么？**
- **TopicExchange**：根据 Routing Key 的通配符匹配绑定队列。`#` 匹配零或多个单词，`*` 匹配一个单词。
- **死信交换机 DLX（Dead Letter Exchange）**：消息消费失败（如抛出异常）时，RabbitMQ 不会丢弃它，而是自动转发到 DLX。专门用一个队列接收死信，便于排查和处理重试。

```
                               payment.exchange (Topic)
          ┌──────────────────────────┼──────────────────────────┐
          │                          │                          │
    payment.result.queue     payment.callback.queue     payment.dlq
    routing: payment.#       routing: callback.#        (死信队列)
          │                          │
          ▼                          ▼
    Notification Service     Transaction Service
```

```java
@Configuration
public class RabbitMQConfig {

    // 1. 主交换机 — Topic 类型
    @Bean
    public TopicExchange paymentExchange() {
        return new TopicExchange("payment.exchange");
    }

    // 2. 支付结果队列（给 Notification Service 消费）
    @Bean
    public Queue paymentResultQueue() {
        return QueueBuilder.durable("payment.result.queue")
                .deadLetterExchange("payment.dlx")         // 失败后进死信
                .deadLetterRoutingKey("payment.dead")
                .build();
    }

    @Bean
    public Binding paymentResultBinding() {
        return BindingBuilder.bind(paymentResultQueue())
                .to(paymentExchange())
                .with("payment.#");                       // 以 payment. 开头的路由键
    }

    // 3. 渠道回调结果队列（给 Transaction Service 消费）
    @Bean
    public Queue callbackResultQueue() {
        return QueueBuilder.durable("payment.callback.queue")
                .deadLetterExchange("payment.dlx")
                .deadLetterRoutingKey("payment.dead")
                .build();
    }

    @Bean
    public Binding callbackResultBinding() {
        return BindingBuilder.bind(callbackResultQueue())
                .to(paymentExchange())
                .with("callback.#");
    }

    // 4. 死信交换机 + 死信队列
    @Bean
    public TopicExchange deadLetterExchange() {
        return new TopicExchange("payment.dlx");
    }

    @Bean
    public Queue deadLetterQueue() {
        return QueueBuilder.durable("payment.dlq").build();
    }

    @Bean
    public Binding deadLetterBinding() {
        return BindingBuilder.bind(deadLetterQueue())
                .to(deadLetterExchange())
                .with("#");                               // 所有死信都进来
    }
}
```

### 7.2 手动 ACK + 消息重试

**为什么需要？**
RabbitMQ 默认自动 ACK——消息一发给消费者就从队列中删除了。如果处理时抛异常，消息就丢失了。手动 ACK 让消费者处理完再确认，处理失败时消息可以重回队列重试。

**原理是什么？**
- **`acknowledge-mode: manual`**：消费者必须主动调用 `channel.basicAck()` 确认，或 `basicNack()` 拒绝
- **`basicAck(deliveryTag, false)`**：确认消息已处理，RabbitMQ 删除消息
- **`basicNack(deliveryTag, false, true)`**：拒绝消息，requeue=true 让消息重回队列重试；requeue=false 进死信队列

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual     # 手动 ACK
        prefetch: 50                 # 每次预取 50 条（批量消费提高吞吐）
    publisher-confirm-type: correlated  # 发布者确认
    publisher-returns: true
```

```java
@Component
public class PaymentResultConsumer {

    @RabbitListener(queues = "payment.result.queue")
    public void handlePaymentResult(
            @Payload PaymentResultEvent event,
            Channel channel,
            @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag) {

        try {
            // 1. 执行业务（发通知给商户）
            notificationService.sendNotify(event.getTransactionId());

            // 2. 成功 → 手动 ACK
            channel.basicAck(deliveryTag, false);
            log.info("Processed payment result: {}", event.getTransactionId());

        } catch (Exception e) {
            log.error("Failed to process payment result", e);

            // 3. 根据重试次数决定：继续重试 或 进死信队列
            var retryCount = getRetryCount(event.getTransactionId());
            if (retryCount < 3) {
                // requeue=true → 重回队列，稍后重试
                channel.basicNack(deliveryTag, false, true);
            } else {
                // requeue=false → 进死信队列
                channel.basicNack(deliveryTag, false, false);
            }
        }
    }
}
```

### 7.3 TraceId 穿透 MQ（消息前后处理器）

**为什么需要？**
一笔请求经过 Gateway → Transaction → MQ → Notification，跨了 HTTP 和 MQ 两种边界。如果 MQ 消息里没有 TraceId，消费端日志就无法串联到原始请求。

**原理是什么？**
RabbitTemplate 的 `setBeforePublishPostProcessors` 在消息**发送前**拦截，把 TraceId 注入到消息的 Headers 中。消费端从消息头提取 TraceId 放入 MDC。这样就做到了 TraceId 的"透传"——跨越 HTTP 和 MQ 两种通信协议。

```java
@Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory) {
    RabbitTemplate template = new RabbitTemplate(connectionFactory);
    template.setMessageConverter(jsonMessageConverter());

    // 发送前拦截 → 注入 TraceId 到消息头
    template.setBeforePublishPostProcessors((MessagePostProcessor) message -> {
        String traceId = TraceContext.getTraceId();
        if (traceId != null) {
            message.getMessageProperties()
                    .setHeader(TraceContext.TRACE_ID_HEADER, traceId);
        }
        return message;
    });
    return template;
}

// 消费端提取 TraceId
@RabbitListener(queues = "payment.result.queue")
public void consume(@Payload String message,
                    @Header(TraceContext.TRACE_ID_HEADER) String traceId) {
    if (traceId != null) {
        MDC.put("traceId", traceId);   // 放入 MDC，后续日志自动携带
    }
    try {
        // 执行业务...
    } finally {
        MDC.clear();
    }
}
```

### 7.4 Outbox 本地消息表模式

**为什么需要？**
支付成功时做了两件事：更新数据库订单状态 + 发送 MQ 通知。这两步不是原子的——如果 DB 更新成功了但 MQ 发送失败（网络抖动、MQ 宕机），商户就永远收不到通知。这叫"双写不一致"。

**原理是什么？**
Outbox 模式把"发 MQ"这一步变成写本地数据库表（同一个 `@Transactional`），然后由后台定时任务扫描这张表，把未发送的消息投递到 MQ。关键点：
1. 业务表 + Outbox 表在**同一个事务**中写入 → 原子性
2. 后台定时任务**异步**扫描 → 投递失败可以无限重试
3. MQ 确认后更新 outbox 状态为 PROCESSED

```
事务内（一起提交）：
  INSERT payment_transaction ...
  INSERT outbox (status='PENDING') ...

事务外（定时轮询）：
  OutboxProcessor:
    SELECT * FROM outbox WHERE status='PENDING' LIMIT 100
    FOR EACH row:
      rabbitTemplate.send(exchange, routingKey, payload)
      UPDATE outbox SET status='PROCESSED'
```

```java
// 1. Outbox 发布器 — 在事务内写入 outbox 表
@Component
public class OutboxPublisher {

    private final OutboxMapper outboxMapper;
    private final ObjectMapper objectMapper;

    @Transactional(propagation = Propagation.MANDATORY)   // 强制要求调用方已开启事务
    public void publish(String aggregateId, String eventType, Object payload) {
        try {
            OutboxEntity entity = OutboxEntity.builder()
                    .aggregateId(aggregateId)
                    .eventType(eventType)
                    .payload(objectMapper.writeValueAsString(payload))
                    .status("PENDING")
                    .build();
            outboxMapper.insert(entity);
        } catch (JsonProcessingException e) {
            throw new RuntimeException("Failed to serialize outbox payload", e);
        }
    }
}

// 2. Outbox 定时处理器 — 扫描 PENDING 消息，投递到 RabbitMQ
@Component
public class OutboxProcessor {

    private final OutboxMapper outboxMapper;
    private final RabbitTemplate rabbitTemplate;

    @Scheduled(fixedDelay = 2000)   // 每 2 秒扫描一次
    public void processPendingOutbox() {
        List<OutboxEntity> pendingList = outboxMapper.selectList(
                new LambdaQueryWrapper<OutboxEntity>()
                        .eq(OutboxEntity::getStatus, "PENDING")
                        .last("LIMIT 100"));

        for (OutboxEntity outbox : pendingList) {
            try {
                // 投递到 RabbitMQ
                rabbitTemplate.convertAndSend(
                        "payment.exchange",
                        "payment." + outbox.getEventType(),
                        outbox.getPayload());

                // 投递成功 → 标记为已处理
                outboxMapper.updateById(OutboxEntity.builder()
                        .id(outbox.getId())
                        .status("PROCESSED")
                        .build());

            } catch (Exception e) {
                log.error("Failed to send outbox message: {}", outbox.getId(), e);
                // 下次扫描继续重试
            }
        }
    }
}

// 3. 业务层使用 — 同一个 @Transactional 中
@Transactional(rollbackFor = Exception.class)
public PaymentTransaction createPayment(CreatePaymentRequest request) {
    // 1. 写业务表
    PaymentTransaction tx = PaymentTransaction.builder()
            .transactionId(generateId())
            .amount(request.getAmount())
            .status("INIT")
            .build();
    paymentMapper.insert(tx);

    // 2. 写 Outbox 表（同一事务）
    outboxPublisher.publish(tx.getTransactionId(), "PAYMENT_CREATED",
            PaymentCreatedEvent.builder()
                    .transactionId(tx.getTransactionId())
                    .amount(tx.getAmount())
                    .build());

    return tx;
    // 两个 insert 要么一起提交，要么一起回滚
}
```

## 8. 中间件 — Nacos

### 8.1 服务注册与发现

**为什么需要？**
微服务数量一多，各服务的 IP 地址变成了动态变化的（扩缩容、宕机重启）。不能把地址硬编码在配置文件里。注册中心让服务启动时上报自己的地址，消费者通过"服务名"获取地址列表，自动做负载均衡。

**原理是什么？**
1. **服务注册**：每个微服务启动时，向 Nacos Server 发送心跳（包含 IP、端口、服务名）
2. **健康检查**：Nacos 每隔几秒检查服务的心跳，收不到就标记为不健康
3. **服务发现**：Gateway 路由 `lb://payment-transaction-service` 中的 `lb://` 告诉 Spring Cloud LoadBalancer 去 Nacos 查询该服务下的所有健康节点
4. **负载均衡**：默认使用轮询（Round-Robin）策略，选择一个节点转发请求

```yaml
# 每个微服务的 application.yml

```

```yaml
# Gateway 的路由 — lb:// 前缀触发负载均衡
```

## 9. 中间件 — Sentinel

### 9.1 网关层限流

**为什么需要？**
高并发下突发流量可能打垮后端。限流在网关层先拦截，超过阈值的请求直接返回 429，不让无效请求到达业务服务。

**原理是什么？**
Sentinel 用"滑动窗口"做统计：把 1 秒分成多个小窗口（比如 500ms 一个），持续计算过去 1 秒内的总请求数。超过阈值时触发 Block。因为限流发生在网关，对后端服务完全透明。

```java
@Configuration
public class SentinelGatewayConfig {

    @PostConstruct
    public void initBlockHandler() {
        // 自定义限流响应 — 默认返回 HTML，改成返回 JSON
        GatewayCallbackManager.setBlockHandler((ServerWebExchange exchange, Throwable t) -> {
            return ServerResponse.status(HttpStatus.TOO_MANY_REQUESTS)
                    .contentType(MediaType.APPLICATION_JSON)
                    .body(BodyInserters.fromValue(Map.of(
                            "code", 429,
                            "message", "触发网关限流，请稍后重试"
                    )));
        });
    }
}
```

## 10. API 鉴权体系 (HMAC-SHA256 + Nonce)

### 10.1 为什么需要？

支付系统暴露在公网上，必须防住两类攻击：
1. **中间人篡改**：攻击者截获请求，把金额 99 改成 0.01，再放行
2. **重放攻击**：攻击者截获一笔成功的请求，不停重放，让商户不断收到重复通知

HMAC-SHA256 签名解决篡改问题：请求的任何字段被修改，签名验证不通过。
Nonce 防重放解决重放问题：同一笔请求的 Nonce 只能使用一次，第二次直接拒绝。

### 10.2 原理是什么？

**签名算法**：
```
signature = HMAC-SHA256(
    HTTP Method + "\n" +
    Request Path + "\n" +
    Timestamp + "\n" +
    Nonce + "\n" +
    SHA256(Request Body) + "\n",
    API Secret
)
```

- **HMAC-SHA256**：带密钥的哈希，密钥（Secret）只有服务端和合法客户端知道。攻击者拿不到密钥，伪造不了签名
- **Timestamp**：检查请求时间是否在 5 分钟内，超过范围的直接拒绝（防止"很久以前"的请求被重放）
- **Nonce**：每个请求一个随机 UUID，服务端记录已使用的 Nonce，5 分钟内再次出现就拒绝（防止"短时间"重放）
- **SHA256(Body)**：对请求体做摘要，body 被改一个字节签名就不同

```
客户端（TestClient / 商户）               Gateway                    后端服务
        │                                  │                          │
        │   POST /api/v1/payments          │                          │
        │   Headers:                       │                          │
        │   X-Api-Key: AK_TEST            │                          │
        │   X-Timestamp: 1700000000000    │                          │
        │   X-Nonce: a1b2c3d4            │                          │
        │   X-Signature: abc123...        │                          │
        │   Body: {"amount":99}          │                          │
        │─────────────────────────────────▶                          │
        │                                  │  验证签名               │
        │                                  │  ① 查 API Key → Secret │
        │                                  │  ② 自己算一次签名       │
        │                                  │  ③ 对比客户端签名       │
        │                                  │  ④ 检查 Nonce 是否已用  │
        │                                  │  ⑤ 检查 Timestamp 偏差  │
        │                                  │  全部通过 → 放行        │
        │                                  │─────────────────────────▶
```

### 10.3 代码怎么写？

```java
// 网关全局 Filter — 每个请求都经过签名验证
@Component
public class ApiSignatureAuthFilter implements GlobalFilter, Ordered {

    private final ApiSignatureAuthProperties authProperties;
    private final InMemoryNonceStore nonceStore;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        String path = request.getURI().getPath();

        // 白名单放行（回调接口、健康检查等）
        if (isWhitelisted(path)) {
            return chain.filter(exchange);
        }

        // 1. 提取签名头
        String apiKey = trimHeader(request, "X-Api-Key");
        String signature = trimHeader(request, "X-Signature");
        String timestamp = trimHeader(request, "X-Timestamp");
        String nonce = trimHeader(request, "X-Nonce");

        String missing = findMissingHeader(apiKey, signature, timestamp, nonce);
        if (missing != null) {
            return unauthorized(exchange, "Missing: " + missing);
        }

        // 2. 检查 Timestamp 是否在允许偏差内（默认 5 分钟）
        long requestTime = Long.parseLong(timestamp);
        long now = Instant.now().toEpochMilli();
        if (Math.abs(now - requestTime) > authProperties.getTimestampSkewSeconds() * 1000L) {
            return unauthorized(exchange, "Timestamp out of range");
        }

        // 3. 检查 Nonce 是否已使用（防重放）
        if (!nonceStore.putIfAbsent(nonce, authProperties.getNonceTtlSeconds())) {
            return unauthorized(exchange, "Nonce already used");
        }

        // 4. 异步读取 body → 验证签名
        return readBody(exchange).flatMap(bodyBytes -> {
            String serverSignature = sign(bodyBytes, apiKey, timestamp, nonce);
            if (!serverSignature.equals(signature)) {
                return unauthorized(exchange, "Signature mismatch");
            }
            // 5. 全部通过 → 注入认证标记，放行
            return chain.filter(exchange.mutate()
                    .request(decorateRequest(request, bodyBytes, apiKey))
                    .build());
        });
    }

    // HMAC-SHA256 签名计算
    private String sign(byte[] bodyBytes, String apiKey, String timestamp, String nonce) {
        String secret = authProperties.getClients().get(apiKey);
        String payload = "POST\n/api/v1/payments\n" + timestamp + "\n" + nonce + "\n"
                + sha256(bodyBytes) + "\n";
        Mac mac = Mac.getInstance("HmacSHA256");
        SecretKeySpec keySpec = new SecretKeySpec(secret.getBytes(UTF_8), "HmacSHA256");
        mac.init(keySpec);
        return bytesToHex(mac.doFinal(payload.getBytes(UTF_8)));
    }

    @Override
    public int getOrder() { return -60; }  // 高优先级，越早执行越好
}
```

**Nonce 存储**：Gateway 排除了 Redis 依赖，用 `ConcurrentHashMap` + `ScheduledExecutorService` 做本地内存存储。

```java
@Component
public class InMemoryNonceStore {
    private final ConcurrentHashMap<String, Long> store = new ConcurrentHashMap<>();
    private final ScheduledExecutorService cleaner =
            Executors.newSingleThreadScheduledExecutor(r -> {
                Thread t = new Thread(r, "nonce-cleaner");
                t.setDaemon(true);
                return t;
            });

    public InMemoryNonceStore() {
        cleaner.scheduleWithFixedDelay(this::evictExpired, 60, 60, TimeUnit.SECONDS);
    }

    // putIfAbsent — 原子操作：不存在才放进去
    public boolean putIfAbsent(String nonce, long ttlSeconds) {
        long expiresAt = Instant.now().toEpochMilli() + ttlSeconds * 1000;
        Long previous = store.putIfAbsent(nonce, expiresAt);
        return previous == null;  // null = 首次写入，非 null = 已存在（重复请求）
    }

    private void evictExpired() {
        long now = Instant.now().toEpochMilli();
        store.values().removeIf(expiresAt -> expiresAt < now);
    }
}
```

## 11. 幂等性设计 (Idempotency)

### 11.1 为什么需要？

支付系统最怕"重复付款"：用户点了支付按钮没反应，又点了一次，结果扣了两笔钱。幂等性保证**同一笔请求无论重复多少次，效果都等于只处理一次**。

核心场景：
- 用户重复点击支付按钮
- 网络重试导致请求被发送多次
- MQ 消息重复投递

### 11.2 原理是什么？

本项目用**三层防护**实现幂等：

| 层级 | 技术 | 作用 |
|------|------|------|
| 第一层：分布式锁 | Redis SETNX | 同一时间内同一幂等键只允许一个请求在处理 |
| 第二层：缓存结果 | Redis 值缓存 | 重复请求直接返回第一次的结果，不重复执行业务 |
| 第三层：数据库乐观锁 | `UPDATE ... WHERE status = expected` | 防止并发覆盖 |

```
第一次请求：
  SETNX idempotent:key IN_PROGRESS → OK
  → 执行业务（写数据库）
  → SET idempotent:key "RESULT:{json}"
  
第二次请求（重复）：
  SETNX idempotent:key IN_PROGRESS → 失败（key 已存在）
  GET idempotent:key → "RESULT:{json}"
  → 直接返回缓存中的结果，不执行业务
```

### 11.3 代码怎么写？

```java
// 1. 定义幂等注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    long ttl() default 86400;              // 24 小时内相同 key 只处理一次
    boolean fetchResult() default true;    // 重复请求是否返回缓存结果
}

// 2. AOP 切面实现幂等逻辑
@Aspect
@Component
public class IdempotentAspect {

    private final IdempotentService idempotentService;

    @Around("@annotation(idempotent)")
    public Object handleIdempotent(ProceedingJoinPoint joinPoint, Idempotent idempotent)
            throws Throwable {
        // 从请求参数中提取幂等键
        String idempotentKey = extractIdempotentKey(joinPoint);

        // 尝试获取分布式锁 + 检查缓存
        boolean acquired = idempotentService.tryAcquire(idempotentKey, idempotent.ttl());
        if (!acquired) {
            if (idempotent.fetchResult()) {
                // 重复请求 → 返回缓存结果
                Optional<String> cached = idempotentService.getCachedResult(idempotentKey);
                if (cached.isPresent()) {
                    return cached.get();
                }
            }
            throw new BizException(ErrorCode.IDEMPOTENT_CONFLICT, "重复请求，请稍后重试");
        }

        try {
            Object result = joinPoint.proceed();    // 执行业务
            idempotentService.markProcessed(idempotentKey, result, idempotent.ttl());
            return result;
        } catch (Exception e) {
            idempotentService.release(idempotentKey);  // 业务失败 → 释放锁
            throw e;
        }
    }
}

// 3. Service 层 Redis 操作
@Service
public class IdempotentServiceImpl implements IdempotentService {
    private final StringRedisTemplate redisTemplate;

    @Override
    public boolean tryAcquire(String idempotentKey, long ttlSeconds) {
        // SET key value NX EX ttl — 原子操作
        return Boolean.TRUE.equals(redisTemplate.opsForValue()
                .setIfAbsent(KEY_PREFIX + idempotentKey, "IN_PROGRESS",
                        ttlSeconds, TimeUnit.SECONDS));
    }

    @Override
    public Optional<String> getCachedResult(String idempotentKey) {
        String value = redisTemplate.opsForValue().get(KEY_PREFIX + idempotentKey);
        if (value != null && value.startsWith("RESULT:")) {
            return Optional.of(value.substring(7));   // 去掉 "RESULT:" 前缀
        }
        return Optional.empty();
    }

    @Override
    public void markProcessed(String idempotentKey, Object result, long ttlSeconds) {
        String json = objectMapper.writeValueAsString(result);
        redisTemplate.opsForValue().set(KEY_PREFIX + idempotentKey,
                "RESULT:" + json, ttlSeconds, TimeUnit.SECONDS);
    }
}
```

## 12. 架构模式与设计模式

### 12.1 责任链模式 — 风控引擎

**为什么需要？**
支付下单前需要做多个风控检查：黑名单、高频限流、大额熔断。如果把这些检查全都写在 Service 方法里，代码又长又难维护。责任链模式把每个规则封装成独立的类，互不干扰，新增规则不用改已有代码。

**原理是什么？**
`RiskRule` 是规则接口，`RiskControlManager` 把 Spring 容器中所有 `RiskRule` 实现收集起来，逐个执行。`@Order` 注解控制执行顺序。某个规则抛异常就阻断交易，全部通过才放行。

```java
// 规则接口
public interface RiskRule {
    void evaluate(RiskContext context) throws RiskException;
}

// 上下文 — 提取风控需要的要素
@Data
@Builder
public class RiskContext {
    private String orderId;
    private String clientIp;
    private BigDecimal amount;
    private String currency;
    private String paymentMethod;
}

// 管理器 — 自动收集所有规则
@Component
public class RiskControlManager {

    private final List<RiskRule> riskRules;  // Spring 自动注入所有 RiskRule 实现

    public RiskControlManager(List<RiskRule> riskRules) {
        this.riskRules = riskRules;
    }

    public void evaluate(RiskContext context) throws RiskException {
        for (RiskRule rule : riskRules) {
            rule.evaluate(context);   // 逐个执行，抛异常就阻断
        }
    }
}

// 规则 1：黑名单检查
@Component
@Order(10)                // 优先级 10，最先执行
public class BlacklistRiskRule implements RiskRule {
    @Override
    public void evaluate(RiskContext context) throws RiskException {
        if (isBlacklisted(context.getClientIp())) {
            throw new RiskException(ErrorCode.RSK_BLACKLIST, "IP 已被加入黑名单");
        }
    }
    private boolean isBlacklisted(String ip) { /* 查 Redis Set 或数据库 */ }
}

// 规则 2：高频限流（INCR + EXPIRE）
@Component
@Order(20)
public class HighFrequencyRiskRule implements RiskRule {
    @Override
    public void evaluate(RiskContext context) throws RiskException {
        String key = "risk:freq:ip:" + context.getClientIp();
        Long count = redisTemplate.opsForValue().increment(key);
        if (count != null && count == 1) redisTemplate.expire(key, 1, TimeUnit.MINUTES);
        if (count != null && count > 10) {
            throw new RiskException(ErrorCode.RSK_HIGH_FREQUENCY, "请求频率过高");
        }
    }
}

// 规则 3：大额熔断
@Component
@Order(30)
public class LargeAmountRiskRule implements RiskRule {
    @Override
    public void evaluate(RiskContext context) throws RiskException {
        if (context.getAmount().compareTo(new BigDecimal("50000")) > 0) {
            throw new RiskException(ErrorCode.RSK_LARGE_AMOUNT, "交易金额超过 5 万限额");
        }
    }
}
```

**执行流程**：
```
下单请求
  │
  ▼
RiskControlManager.evaluate(context)
  │
  ├── BlacklistRiskRule.evaluate()  @Order(10)
  │     └── IP 在黑名单中？→ 是 → 阻断
  │
  ├── HighFrequencyRiskRule.evaluate()  @Order(20)
  │     └── 1 分钟内超过 10 次？→ 是 → 阻断
  │
  ├── LargeAmountRiskRule.evaluate()  @Order(30)
  │     └── 金额 > 5 万？→ 是 → 阻断
  │
  └── 全部通过 → 创建支付单
```

### 12.2 策略模式 + 工厂模式 — 渠道适配

**为什么需要？**
微信和支付宝的支付 API、加密方式、参数格式完全不同。如果在核心代码里写 `if (channel == WECHAT) { wechatPay() } else if (channel == ALIPAY) { alipayPay() }`，每接一个渠道就要改核心代码，迟早变成"if 地狱"。

**原理是什么？**
- **策略模式**：定义统一接口 `PayChannelStrategy`，每个渠道写一个实现类
- **工厂模式**：`ChannelStrategyFactory` 在 Spring 启动时自动收集所有策略，按 `channelCode` 缓存在 Map 中
- **防腐层（ACL）**：交易服务只通过 Feign 调用渠道服务，完全不接触微信/支付宝的 SDK

```java
// 策略接口
public interface PayChannelStrategy {
    String getChannelCode();                          // 渠道标识：WECHAT、ALIPAY
    ChannelPayResponse pay(UnifiedPayRequest request); // 统一支付方法
    ChannelPayResponse refund(UnifiedRefundRequest request);
}

// 微信支付实现
@Component
public class WechatPayStrategy implements PayChannelStrategy {
    @Override
    public String getChannelCode() { return "WECHAT_PAY"; }

    @Override
    public ChannelPayResponse pay(UnifiedPayRequest request) {
        // 调用微信 SDK V3 API...
        return ChannelPayResponse.builder()
                .providerPayUrl("weixin://pay/...").
                .build();
    }
}

// 支付宝支付实现
@Component
public class AlipayStrategy implements PayChannelStrategy {
    @Override
    public String getChannelCode() { return "ALIPAY"; }

    @Override
    public ChannelPayResponse pay(UnifiedPayRequest request) {
        // 调用支付宝 SDK...
        return ChannelPayResponse.builder()
                .providerPayUrl("alipay://pay/...")
                .build();
    }
}

// 工厂 — Spring 启动时自动装配
@Component
public class ChannelStrategyFactory {

    private final Map<String, PayChannelStrategy> strategyMap;

    public ChannelStrategyFactory(List<PayChannelStrategy> strategies) {
        this.strategyMap = strategies.stream()
                .collect(Collectors.toMap(
                        PayChannelStrategy::getChannelCode,
                        Function.identity()));
    }

    public PayChannelStrategy getStrategy(String channelCode) {
        PayChannelStrategy strategy = strategyMap.get(channelCode);
        if (strategy == null) {
            throw new BizException("不支持的支付渠道: " + channelCode);
        }
        return strategy;
    }
}

// 使用 — 新增渠道只需加一个实现类，核心代码零改动
@RequiredArgsConstructor
@Service
public class ChannelPayServiceImpl implements ChannelPayService {

    private final ChannelStrategyFactory strategyFactory;

    public ChannelPayResponse pay(UnifiedPayRequest request) {
        PayChannelStrategy strategy = strategyFactory.getStrategy(request.getChannelCode());
        return strategy.pay(request);   // 多态！一行代码搞定所有渠道
    }
}
```

### 12.3 状态机模式 — 支付状态流转

**为什么需要？**
支付单有一整套状态：INIT → PENDING → SUCCESS/FAILED/CLOSED。状态之间有严格的流转规则（比如 SUCCESS 不能直接回到 INIT）。如果每个 Service 方法里手动用 if 判断状态，容易遗漏规则，导致"状态混乱"。

**原理是什么？**
支付系统中状态机是通过**乐观锁 + 枚举**实现的轻量级方案——没有引入复杂的状态机框架（如 Spring Statemachine），而是用 `UPDATE ... WHERE status = expectedStatus` 保证原子性：

```
   INIT ──→ PENDING ──→ SUCCESS
     │                    │
     └──→ CLOSED          └──→ FAILED
          (超时关单)            (支付失败)
```

```java
// 状态枚举
public enum PaymentStatus {
    INIT("INIT"), PENDING("PENDING"), SUCCESS("SUCCESS"),
    FAILED("FAILED"), CLOSED("CLOSED");

    public boolean canTransitionTo(PaymentStatus target) {
        return switch (this) {
            case INIT     -> target == PENDING || target == CLOSED;
            case PENDING  -> target == SUCCESS || target == FAILED || target == CLOSED;
            case SUCCESS,
                 FAILED,
                 CLOSED   -> false;   // 终态，不可再变
        };
    }
}

// Mapper — 乐观锁：只有 status = expected 时才更新
@Update("UPDATE payment_transaction SET status = #{newStatus} " +
        "WHERE transaction_id = #{txId} AND status = #{expectedStatus}")
int updateStatusAtomic(String txId, String newStatus, String expectedStatus);

// Service — 更新前检查状态流转合法性
@Transactional(rollbackFor = Exception.class)
public void updateStatus(String transactionId, PaymentStatus target) {
    PaymentTransaction tx = paymentMapper.selectByTransactionId(transactionId);
    PaymentStatus current = PaymentStatus.fromCode(tx.getStatus());

    if (!current.canTransitionTo(target)) {
        throw new BizException("状态不合法: " + current + " → " + target);
    }

    int rows = paymentMapper.updateStatusAtomic(
            transactionId, target.getCode(), current.getCode());
    if (rows == 0) {
        // 乐观锁失败 — 被别人并发改了
        throw new BizException("交易状态已被变更，请刷新后重试");
    }
}
```

### 12.4 防腐层模式 (ACL) — 渠道隔离

**为什么需要？**
传统支付系统把微信 SDK、支付宝 SDK 直接写在交易服务中，导致：
1. SDK 版本冲突（微信用 OkHttp 3，支付宝用 OkHttp 4）
2. 渠道 API 升级必须重新部署核心系统
3. 安全性问题：渠道密钥暴露在核心代码中

**原理是什么？**
防腐层（Anti-Corruption Layer）在交易服务和渠道 SDK 之间建一道墙。交易服务只通过 Feign 调用渠道服务，传递统一的标准 DTO。渠道服务内部完成 SDK 调用、加解密、回调解析。渠道 API 升级只改渠道服务，交易服务不受影响。

```
交易服务                   渠道服务（防腐层）              第三方
┌────────────────┐   Feign   ┌────────────────┐   SDK    ┌──────────┐
│ Transaction     │─────────▶│ Channel         │─────────▶│ 微信支付  │
│ Service         │          │ Service (ACL)   │          │ 支付宝    │
│                 │◀────────│                  │◀────────│          │
│ 只认识标准 DTO  │          │ 封装 SDK 细节    │          │ 各种协议  │
└────────────────┘          └────────────────┘          └──────────┘
```

```java

        // 内部路由到对应的渠道策略
```

## 13. 可观测性 — 链路追踪与日志

### 13.1 TraceId 全链路透传

**为什么需要？**
一笔支付请求经过 Gateway → Transaction Service → Channel Service（Feign）→ RabbitMQ → Notification Service。如果出问题，需要登录 4 个服务看日志，没有 TraceId 根本串不起来。

**原理是什么？**
在请求入口生成一个全局唯一的 TraceId，通过三个方式透传到所有下游：
1. **HTTP 透传**：Gateway Filter 生成 TraceId，Feign 拦截器放入请求头
2. **MQ 透传**：RabbitTemplate 发送前注入到消息头，消费端提取
3. **MDC 存储**：所有服务通过 `%X{traceId}` 日志 pattern 自动输出

```
Gateway                  Transaction               Notification
   │                         │                         │
   │ 生成 TraceId=T123       │                         │
   │ MDC.put("traceId",T123) │                         │
   │                         │                         │
   │──Feign──▶ T123 in Header│                         │
   │                         │ MDC.put("traceId",T123) │
   │                         │                         │
   │                         │──MQ──▶ T123 in Header   │
   │                         │                         │ MDC.put("traceId",T123)
   │                         │                         │
   ▼                         ▼                         ▼
日志:[T123] 收到请求      日志:[T123] 处理支付      日志:[T123] 发送通知
```

```java
// 1. Gateway Filter — 生成 TraceId 放入 MDC
@Component
@ConditionalOnWebApplication(type = SERVLET)
public class TraceIdFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        try {
            String traceId = null;
            if (request instanceof HttpServletRequest httpRequest) {
                traceId = httpRequest.getHeader("X-Trace-Id");
            }
            if (!StringUtils.hasText(traceId)) {
                traceId = UUID.randomUUID().toString().replace("-", "");
            }
            MDC.put("traceId", traceId);  // 放入 MDC，日志自动输出
            chain.doFilter(request, response);
        } finally {
            MDC.clear();                  // 必须清理！否则线程池复用时串号
        }
    }
}

// 2. Feign 拦截器 — 透传 TraceId 到下游 HTTP 服务
@Component
public class FeignTraceInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        String traceId = MDC.get("traceId");
        if (traceId != null) {
            template.header("X-Trace-Id", traceId);  // 放入请求头
        }
    }
}

// 3. RabbitMQ 透传 — 发送前注入 TraceId
@Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory) {
    RabbitTemplate template = new RabbitTemplate(connectionFactory);
    template.setBeforePublishPostProcessors(message -> {
        String traceId = MDC.get("traceId");
        if (traceId != null) {
            message.getMessageProperties().setHeader("X-Trace-Id", traceId);
        }
        return message;
    });
    return template;
}

// 4. 日志配置 — %X{traceId} 输出 MDC 值
// logback-spring-base.xml
<encoder>
    <pattern>
        %d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId}] - %msg%n
    </pattern>
</encoder>
```

### 13.2 AOP 耗时监控

**为什么需要？**
系统变慢时要知道慢在哪：是 Controller 层慢？Service 层慢？还是数据库慢？AOP 切面在方法调用前后打时间戳，自动生成耗时日志。

**原理是什么？**
`@Around` 通知在方法执行前后记录时间差，超过阈值（如 500ms）输出 WARN 级别日志。

```java
@Aspect
@Component
@ConditionalOnWebApplication(type = SERVLET)
public class WebLogAspect {

    @Pointcut("execution(public * com.payment.core..controller.*.*(..))")
    public void controllerLog() {}

    @Around("controllerLog()")
    public Object doAround(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = joinPoint.proceed();
            long duration = System.currentTimeMillis() - start;
            log.info("{} 耗时={}ms", joinPoint.getSignature().getName(), duration);
            return result;
        } catch (Throwable e) {
            long duration = System.currentTimeMillis() - start;
            log.error("{} 失败, 耗时={}ms", joinPoint.getSignature().getName(), duration, e);
            throw e;
        }
    }
}
```

## 14. 统一异常体系

### 14.1 为什么需要？

没有统一异常处理时，每个 Controller 的异常处理不一致：
- 有的返回 `{ "code": 400, "message": "参数错误" }`
- 有的返回 `{ "errorCode": "INVALID", "msg": "..." }`
- 有的直接抛 500 给客户端（暴露了堆栈信息）

统一异常体系让所有错误响应格式一致，前端统一处理。

### 14.2 原理是什么？

三个部分组成：
1. **错误码枚举**：按模块划分错误前缀，快速定位问题来源
2. **业务异常类**：携带错误码和参数，不直接在代码里写中文
3. **全局异常处理器**：用 `@ControllerAdvice` 拦截所有异常，统一格式输出

### 14.3 代码怎么写？

```java
// 1. 错误码枚举
public enum ErrorCode {
    // 系统级
    SYS_INTERNAL_ERROR("SYS_500", "系统内部错误"),
    SYS_PARAM_INVALID("SYS_400", "参数校验失败"),

    // 支付
    PAY_AMOUNT_INVALID("PAY_400", "金额不合法"),
    PAY_STATUS_INVALID("PAY_400", "支付状态不合法"),

    // 风控
    RSK_HIGH_FREQUENCY("RSK_429", "请求频率过高，请稍后重试"),
    RSK_BLACKLIST("RSK_403", "IP 已被加入黑名单"),
    RSK_LARGE_AMOUNT("RSK_400", "交易金额超过限额"),

    // 幂等
    IDEMPOTENT_CONFLICT("IDEM_409", "重复请求");

    private final String code;
    private final String message;
    // constructor + getter ...
}

// 2. 业务异常类
public class BizException extends RuntimeException {
    private final String errorCode;
    private final String errorMessage;

    public BizException(ErrorCode errorCode) {
        super(errorCode.getCode() + ": " + errorCode.getMessage());
        this.errorCode = errorCode.getCode();
        this.errorMessage = errorCode.getMessage();
    }
}

// 3. 全局异常处理器
@ControllerAdvice
@ConditionalOnWebApplication(type = SERVLET)
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public ApiResponse<Void> handleBiz(BizException e) {
        log.warn("BizException: {} {}", e.getErrorCode(), e.getErrorMessage());
        return ApiResponse.error(e.getErrorCode(), e.getErrorMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ApiResponse<Void> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ":" + f.getDefaultMessage())
                .collect(Collectors.joining("；"));
        return ApiResponse.error("SYS_400", msg);
    }

    @ExceptionHandler(Exception.class)
    public ApiResponse<Void> handleUnknown(Exception e) {
        log.error("Unhandled exception", e);
        return ApiResponse.error("SYS_500", "系统繁忙，请稍后重试");
    }
}
```

```java
// ApiResponse — 统一响应格式
@Data
@Builder
@JsonInclude(Include.NON_NULL)
public class ApiResponse<T> implements Serializable {
    private int code;
    private String message;
    private T data;
    private long timestamp;

    public static <T> ApiResponse<T> success(T data) {
        return ApiResponse.<T>builder()
                .code(200).message("success").data(data)
                .timestamp(Instant.now().toEpochMilli())
                .build();
    }

    public static ApiResponse<Void> error(String errorCode, String message) {
        return ApiResponse.<Void>builder().code(400)
                .message(errorCode + ":" + message)
                .timestamp(Instant.now().toEpochMilli())
                .build();
    }
}
```

### 15.2 请求拦截与登录态

**为什么需要？**
每个 API 请求都要做三件事：1) 注入认证 Token；2) 统一处理错误响应；3) 401 时自动跳转登录页。如果每个请求都手动写一遍，代码大量重复。

**原理是什么？**
Axios 拦截器在请求发起前注入 Token，在响应返回后拦截错误码，401 时清除登录态并跳转登录页。

```typescript
// request.ts — 统一请求层
const http = axios.create({
    baseURL: 'http://localhost:8080/api/v1/admin',
    timeout: 15000
})

// 请求拦截器 — 注入 Token
http.interceptors.request.use(config => {
    const token = sessionStorage.getItem('token')
    if (token) {
        config.headers.Authorization = `Bearer ${token}`
    }
    return config
})

// 响应拦截器 — 统一错误处理
http.interceptors.response.use(
    response => response.data,   // 直接返回 data，不用每处写 .data
    error => {
        if (error.response?.status === 401) {
            sessionStorage.removeItem('token')
            router.push('/login')    // Token 过期 → 跳转登录
            ElMessage.error('登录已过期，请重新登录')
        } else {
            ElMessage.error(error.response?.data?.message || '操作失败')
        }
        return Promise.reject(error)
    }
)
```

### 15.3 路由守卫

**为什么需要？**
未登录用户访问后台页面应该自动跳转到登录页，不能等到请求 API 时才发现 401。

```typescript
// router/index.ts
const router = createRouter({
    history: createWebHistory(),
    routes: [
        { path: '/login', component: LoginPage, meta: { requiresAuth: false } },
        { path: '/dashboard', component: DashboardPage, meta: { requiresAuth: true } },
        { path: '/transactions', component: TransactionsPage, meta: { requiresAuth: true } },
        { path: '/:pathMatch(.*)*', redirect: '/login' }
    ]
})

// 全局前置守卫
router.beforeEach((to, from, next) => {
    const token = sessionStorage.getItem('token')
    if (to.meta.requiresAuth && !token) {
        next('/login')       // 需要登录 → 跳到登录页
    } else {
        next()               // 已登录或不需要登录 → 放行
    }
})
```

### 16.1 Docker Compose 一键启动

**为什么需要？**
项目依赖 MySQL、Redis、RabbitMQ、Nacos、Sentinel 5 个中间件。如果每个都手动安装配置，新成员加入环境需要半天。Docker Compose 一条命令启动所有依赖。

```yaml
# docker-compose.yml（核心中间件部分）
services:
  payment-mysql:
    image: mysql:8.0
    container_name: payment-mysql
    environment:
      MYSQL_ROOT_PASSWORD: root
    ports:
      - "3306:3306"
    volumes:
      - ./db/mysql/init:/docker-entrypoint-initdb.d  # 自动初始化数据库和表

  payment-redis:
    image: redis:7.0-alpine
    container_name: payment-redis
    ports:
      - "6379:6379"

  payment-rabbitmq:
    image: rabbitmq:3.12-management-alpine
    container_name: payment-rabbitmq
    ports:
      - "5672:5672"     # AMQP 通信
      - "15672:15672"   # 管理控制台
    environment:
      RABBITMQ_DEFAULT_USER: guest
      RABBITMQ_DEFAULT_PASS: guest

  payment-nacos:
    image: nacos/nacos-server:v2.2.3
    container_name: payment-nacos
    environment:
      - MODE=standalone
    ports:
      - "8848:8848"     # API 管理端口
      - "9848:9848"     # gRPC 端口

  payment-sentinel:
    image: bladex/sentinel-dashboard:1.8.6
    container_name: payment-sentinel
    ports:
      - "8858:8080"     # Sentinel 控制台
```
